## TASK 004 — Gödel prime ledger (blocker (a) repair)

The normative text is **[SPEC.md](SPEC.md)**; this README is the summary.

**Factorization gives exact recoverability, NOT physical immutability.** Anyone who holds `L`
can compute a different integer `L'` for a different history; nothing in the arithmetic stops
the number from being replaced, truncated or rewritten. What the construction guarantees is
that a given `L` determines its history exactly and uniquely (fundamental theorem of
arithmetic), and that malformed integers are detected. Tamper *evidence* requires an external
anchor (a commitment held by someone else, a signature, a monotonic counter).

### Two encodings, mode always explicit

`lrd_godel_mode_t` is passed to `lrd_godel_init(g, mode)`, stored in `g->mode`, checked on every
operation (`cfg->mode != g->mode` → `E_MODE`) and written into the exported record. A bare integer
`L` has **no** mode tag: `L = 210` is four empty records in `bij256-records` mode and one empty
record in `positional` mode. Never interpret an `L` without its mode.

| Mode | Use | Layout | Size of `L` |
|---|---|---|---|
| `LRD_GODEL_POSITIONAL` | **real LRD-REC-v1 records (≥ 64 bytes, ~1 KB tested)** | one prime per *byte* of a framed stream | `log2 L ≤ 256·Σ log2 p_k` (n log n growth) |
| `LRD_GODEL_BIJ256_RECORDS` / `_BYTES` (aliases `LRD_GODEL_RECORDS` / `_BYTES`) | **tiny items only (≤ 2 bytes)**, kept for backward compatibility | one prime per *item*, exponent = bijective-base-256 + 1 | exponential in item length |

**Positional encoding.** The ledger is one byte stream `S`: per record, `be32(len(body)) || body`,
where `body` is the canonical LRD-REC-v1 serialization without the constant 11-byte magic
`LRD-REC-v1\n` (restored on decode). Byte `S[k]` goes to the `(k+1)`-th prime with exponent
`S[k]+1 ∈ 1..256`: `L = ∏ p_{k+1}^(S[k]+1)`. Append multiplies; decode is exact division, then strict
framing and canonical-record checks. Exponent 0 never occurs, so "prime absent" is never
confused with "byte present".

**bij256 (tiny records only).** `L = ∏ p_i^(bij256(s_i)+1)`, one prime per item. `log2 L` is
exponential in item length: the 7-byte body of `1:a1:b\n` has a 54-bit exponent and is refused
(`too_big`); only ≤ 2-byte bodies fit under 2^23 bits. Do not use for real records.

### Constants (in `include/lrd_godel.h`)

| Constant | Value | Meaning |
|---|---|---|
| `LRD_GODEL_MAX_LEN` | 1024 | max items (records) per ledger; item 1025 → `E_LEN` (`too_many_items`), checked **before** the item is read or anything is allocated; item 1024 succeeds |
| `LRD_GODEL_POSITIONAL_DEFAULT_MAX_BITS` | 2^26 (8 MiB of `L`) | default `cfg.max_bits`, positional |
| `LRD_GODEL_BIJ256_DEFAULT_MAX_BITS` | 2^23 (1 MiB of `L`) | default `cfg.max_bits`, bij256 |
| `LRD_PRIME_MAX_INDEX` | 65536 | largest supported prime index; `p_65536 = 821641` (checked against an independent sieve) |

Whichever limit is hit first applies: item count, `max_bits` (→ `E_TOOBIG`), or prime index
(→ `E_PRIMECAP`). With the default 2^26 bits the code measures a worst-case (all-0xff bytes) capacity of 16 518
stream bytes; ordinary text uses fewer bits per byte, so more fits, but this is **not** unbounded.

### Prime source

`lrd_prime(i)`: incremental exact trial division (no probabilistic test; `mpz_nextprime` is not
used). Deterministic and exact for `1 ≤ i ≤ LRD_PRIME_MAX_INDEX`. **Failure token beyond the cap:**
`lrd_prime(0)` and `lrd_prime(i > 65536)` return `0`; ledger operations that need such a prime
return `LRD_GODEL_E_PRIMECAP` (`prime_index_above_cap`). Checked-in reference table:
`tests/ledger/primes_first1000.txt` (first 1000 primes, generated by an independent awk loop),
sha256 `22db001956f3a84aa74fcb0bce32118f0ba802dff771f5db94aba7ba5748af0a` (pinned in
`tests/ledger/test_godel.c`, verified with libcrypto). The prime table is a process-global cache and is not thread-safe.

### Rejected encodings (decode / parse)

`L ≤ 0` → `E_NOTPOS` (also at `lrd_godel_parse_hex` and for any parsed exponent `≤ 0`, `parse_factored`);
exponent 0 / missing prime → `E_GAP` (a later sequence prime divides `L`) or `E_ZEROEXP` (positional, inside a
record frame); exponent outside 1..256 (positional) → `E_EXPRANGE`; unknown factor (non-sequence prime
or composite cofactor) → `E_EXTRA`; truncated framing → `E_FRAMING`; a body that is not a canonical
LRD-REC-v1 record → `E_NONCANON`; a non-prime base in `parse_factored` → `E_ARG`.

### Genesis convention

`seq 0` is the **empty ledger**: `L = 1`, `n = 0`, no prime used, in every mode. The first
successful append yields `seq 1`; `seq` equals the number of appended records, one append per
`seq`, in ingestion order. In `ledger/abi/lrd_state.h`, `LRD_GENESIS_COMMIT` (line 52) is the
64-character string of 64 zeros (`000…0`), the `commit` field of the seq-0 state, so the first
transition has `seq = 1 = prev seq + 1`. Test: `godel_genesis_seq0_convention`.

### Known limits (honest)

* The positional `L` grows as n log n in the stream length with constant up to 256; a 1217-byte
  real record produced a 1 103 517-bit `L` and decoding it took about 0.6 s (measured, see the test INFO lines).
* `lrd_godel_append_envelope` is a **marker-only hack**: it appends a zero-length marker item (exponent 1) in `bij256-bytes` mode;
  the envelope and its SHA-256 are built but the payload is **not** encoded in `L` (bound only through the caller-held hash). Do not rely on it for storing data. It requires `bij256-bytes` mode.
* Bare `L` is mode-ambiguous (above).
